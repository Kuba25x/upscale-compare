# Upload and image validation resource limits

Share Comparison stage 1 bounds application-controlled allocations and structural
validation work. It does not establish production CPU suitability or a billing cap.
The frontend comparison tools and original image encoding are unchanged.

Stage 7 now requires zero charges on Workers/D1 Free and included R2 Standard.
The ceilings below are implementation limits, not certified Free-safe upload
sizes. Production deployment is locked; see [the Free-only resource plan and
local diagnostics](FREE_TIER_OPERATIONS.md) before choosing any publication limits.

## Limits

| Resource                                          | Ceiling                                         |
| ------------------------------------------------- | ----------------------------------------------- |
| Image file                                        | 20 MiB                                          |
| Combined original files                           | 40 MiB                                          |
| Buffered HTTP body, including multipart overhead  | 40 MiB + 64 KiB                                 |
| Image dimensions                                  | 36,000,000 pixels; 16,384 pixels per side       |
| PNG/WebP chunks or JPEG outer marker segments     | 4,096 per image                                 |
| Compressed PNG input supplied to the decompressor | At most 8 KiB per pull                          |
| Multipart parts                                   | 6: manifest, optional challenge, up to 4 images |
| Headers per multipart part                        | 4 KiB                                           |
| Multipart boundary                                | 1–70 ASCII characters                           |
| Manifest                                          | 16,000 characters and 64,000 encoded bytes      |
| Challenge                                         | 2,048 characters and 8,192 encoded bytes        |
| Active buffered publications per Worker isolate   | 1, including validation and R2 writes           |
| Waiting publications per isolate                  | 2, with bodies unread by application code       |
| Body receive deadline after admission             | 120 seconds                                     |

Operator configuration may lower the file, total-byte, pixel and side-length
limits. It cannot raise them above these ceilings. Raising a ceiling requires a
code change and renewed resource testing. This is separate from D1 storage quota.

## Allocation and parsing

The Worker uses a narrow parser for the browser's multipart form. It allocates one
body buffer, sized to the declared Content-Length or the configured bounded
maximum when the length is unknown. It enforces the received byte count as well
as any declared length. Image entries reference slices of that buffer through
validation and sequential R2 writes. There are no native FormData/File allocations
or per-file arrayBuffer copies in the upload handler.

Header and field parsing is bounded. Unknown fields, duplicate text fields,
duplicate headers, unsupported part headers, malformed UTF-8 text, file-valued
metadata, missing file dispositions and trailing multipart data are rejected.
Boundary search is linear in input length, including repeated near-matches within
binary files. Files are never decoded as text or re-encoded.

The parser accepts the multipart shape generated by browser FormData, including
quoted boundaries and UTF-8 filenames (which are ignored). It intentionally
rejects preambles, epilogues and content-transfer encodings. Rejected bodies are
cancelled. A receive deadline or an aborted request signal returns 408; saturated admission returns 503. Aborted waiters leave the queue without retaining admission.

One publication holds admission until its R2 writes or cleanup finish. Waiting
requests do not allocate application upload buffers. Reads, deletion and health
checks use their existing routes. This gate protects an individual isolate; it
does not limit publications across isolates, replace rate limiting, or cap cost.

## Image validation

Each container has a fixed structural item ceiling. Valid files with unusually
fragmented containers can therefore be rejected even below the byte/pixel limits.
The application reports an error and never silently recompresses them.

PNG validation still checks chunk order, CRCs, dimensions, scanline filters and
the complete bounded decompressed raster. Compressed data is pulled in small
pieces under stream backpressure. Empty IDATs do not become stream queue entries.
JPEG entropy scanning remains linear in file size; JPEG/WebP remain structurally
validated rather than fully decoded.

## Verification and remaining limits

Regression tests cover excessive image structure, legal fragmented PNGs, bounded
decompressor input, a complete RGBA 8K raster, multipart fragmentation/malformed
inputs, declared and actual lengths, byte limits, timeouts and admission recovery.
Workerd integration tests cover rejection before quota/R2 storage, concurrent
publications, four-image uploads and exact byte identity of two 20 MiB originals
in a 40 MiB publication. Fixtures are generated, not committed large files.

A local Node.js 24 diagnostic against the stage baseline accepted a 1,200,068-byte
PNG with 100,000 empty IDATs in approximately 9,654 ms, with approximately 62 MB
of synchronous heap growth. The updated validator rejected it in approximately
4 ms, with approximately 4.5 MB of synchronous heap growth. These one-run
diagnostics show the regression and early rejection; they are not stable test
thresholds, peak-memory measurements or Cloudflare production CPU measurements.

The buffer ceiling does not account for all runtime, network, decompressor or R2
internal allocations. Backpressure bounds submitted input, not a provider's
internal implementation. Local workerd success does not prove a production
128 MB isolate memory margin or the Workers Free CPU budget. Production workload
measurements remain required before enabling uploads.

This stage leaves publication recovery, quota/cleanup failure handling, global
cost controls, Turnstile rollout and deployment to their separately approved
stages. No production resources or uploads are enabled.
